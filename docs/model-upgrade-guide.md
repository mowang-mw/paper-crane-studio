# 模型升级指南

## 核心原则

平台不与某一个模型绑定。Script、Image、Audio 的运行时差异被限制在 Provider 边界内，Job 快照负责冻结选择和参数，Media Pipeline 消费稳定的 ScriptV1、PNG 与 WAV。这使模型能够按能力替换，但不意味着任意模型可以零适配、零验证地接入。

> 模型决定生成质量上限，平台决定模型能否被稳定、可追溯、可组合地用于生产流程。

## 两类升级不要混淆

### 模型质量上限

更大的或更强的同类模型可能改善：

- 剧本复杂度、叙事连贯性和指令遵循。
- 图片细节、审美质量、提示词理解和单帧角色稳定性。
- TTS 的自然度、情绪、韵律和发音。

这些改进通常可以通过替换对应 Provider 的底层模型获得，但仍需要在目标硬件上验证显存、速度、输出契约和许可证。

### 平台未来能力

以下能力不是简单换大模型就会自动出现：

- 跨镜头角色身份、服装和场景连续性控制。
- 自动分镜规划、镜头语言评估和人工审核闭环。
- 更丰富的局部动作、镜头编辑和专业时间线。
- 角色级连续动作视频生成，以及新的 VideoProvider 工作流。

它们需要新增数据契约、控制条件、任务阶段和验收方法，是平台层扩展。

## 三种部署档位

| 档位 | 状态 | 推荐资源与模型方向 | 保持不变的核心 | 主要取舍 |
| --- | --- | --- | --- | --- |
| Local Demo | **已实际验证** | RTX 4060 8GB；量化 Qwen3-4B、Animagine XL 4.0、Qwen3-TTS 0.6B；顺序 GPU 调度 | Provider、Job 快照、ScriptV1、Media、Manifest | 可本地完整演示；生成质量和速度受轻量模型及显存限制 |
| Workstation | **架构扩展建议，未在本项目验证** | 24GB+ VRAM；更大的剧本模型、更高质量图片/TTS 模型 | 沿用 Provider/Job/Media 契约 | 可提高质量或减少交接，但要重新评估显存、耗时和模型许可证 |
| Cloud / Server | **架构扩展建议，未在本项目验证** | 高端 GPU 服务或闭源 API；可选更大 LLM、图像和 TTS 服务 | 保留任务快照、来源追溯和媒体契约 | 需要鉴权、费用、限流、隐私、远程重试和服务可用性设计 |

本项目没有对 24GB/48GB 工作站、云 GPU 或闭源 API 做实测，因此不能把这些档位描述为已经可用的部署方案。

## 替换 ScriptProvider

1. 实现现有 ScriptProvider 接口，接收故事、风格、镜头数和调用上下文。
2. 将模型输出转换为 ScriptV1，并执行与当前实现相同的结构、引用和数量校验。
3. 使用新的唯一 Provider ID，记录模型 ID、版本/revision、运行时和关键生成参数。
4. 在创建 Job 时把 Provider 与参数写入请求快照；重试必须沿用原快照。
5. 增加成功、格式修复、超时、无效 JSON 和不允许静默 Mock fallback 的测试。

若使用闭源 API，至少需要在 Provider 内新增鉴权、请求/响应映射、限流与重试策略以及错误转换，并继续保持 ScriptV1 或对应媒体资产的数据契约；不要让 API 特有字段泄漏进 ScriptV1。

## 替换 ImageProvider

1. 实现逐镜头图像生成接口，消费 ScriptV1 中的角色、场景和镜头提示。
2. 为每个 shot 返回可解码 PNG，以及模型、revision、seed、尺寸和参数追溯。
3. 保持 shot ID 一一对应，并遵守项目媒体目录边界。
4. 在真实媒体入口继续执行数量、Provider 一致性、哈希、路径和解码校验。
5. 验证现有 FFmpeg 运动、字幕、Poster 与 Manifest 不依赖特定图像模型私有格式。

升级图片模型可能改善单帧质量，但跨镜头角色一致性通常还需要参考图、角色资产或条件控制等平台能力。

## 替换 AudioProvider

1. 实现逐镜头语音接口，消费旁白文本、语言和音色选择。
2. 输出媒体层支持的 WAV，并记录实际时长、采样率、声道、模型和音色。
3. 保持旁白完整性；TimingPlan 可以延长镜头，但不应裁掉语音。
4. 验证公共 audio URL、背景音 ducking、最终混音和 Manifest 追溯。
5. 对损坏音频、空音轨、模型失败和不允许静默 Mock fallback 建立测试。

## VideoProvider 的未来位置

当前项目没有真实 VideoProvider，也没有角色连续动作生成。未来若引入图生视频或文生视频，建议新增明确的 `VideoProvider` 阶段，而不是把视频模型藏进现有 ImageProvider 或 FFmpeg：

```text
ScriptV1 -> Keyframe / Control Assets -> VideoProvider -> Shot Clips -> Media Pipeline
```

这需要定义片段时长、帧率、角色/镜头控制、失败重试、音画同步和来源追溯。现有 FFmpeg 层仍可负责字幕、旁白、背景音、拼接、Poster 和最终封装。该方案只是架构建议，尚未实现或验证。

## 升级验收清单

- Provider ID、模型 ID、版本和许可证信息可追溯。
- 同一请求快照可重试，且不会因全局默认值变化而变更语义。
- 输出符合 ScriptV1/PNG/WAV 契约并可由公共媒体层消费。
- 真实 Provider 失败不会被伪装为 Mock 成功。
- 8GB 环境仍按阶段交接；更大硬件档位单独记录实测结果。
- Manifest 能说明素材最初来源与当前任务是否复用。
