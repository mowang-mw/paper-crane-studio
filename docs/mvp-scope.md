# 当前范围内的 MVP 范围

## 1. 范围判断

“故事 → 结构化剧本 → 角色/场景 → 3—5 分镜 → 关键帧 → 镜头运动 → 旁白/字幕 → 20—40 秒 MP4”作为当前范围上限是合理的。“当前范围”不是必须消耗的工期：应尽快交付可运行成品，剩余时间用于真实模型、质量、稳定性与展示优化。范围同时满足四个限制：

1. 每阶段只做支撑垂直链路所需的最小编辑能力，不做专业创作软件。
2. 全 Mock 和 FFmpeg 是工程保底；至少一个真实文本模型和一个真实图像模型是真实 Provider 完成目标。
3. 固定演示控制为单主角、一个关键道具、最多两个场景、四个镜头。
4. 首先用最小纵向链路产出可播放 MP4，再补完整 UI、数据关系与可靠性；真实模型不破坏离线保底。

因此，MVP 的重点是“可编排、可审核、可追溯、可降级”的生产流程，而不是每一步都达到商业动画质量。

## 2. 两类完成标准

### 2.1 工程保底（P0）

- 无网络、无 API Key、无真实模型时，全 Mock + FFmpeg 可从故事离线导出合规 MP4。
- 第一段 MP4 在里程碑 M1 出现，不等待完整 React 工作区、全部实体字段或高级 Job 可靠性。
- 最终工程保底仍需补齐最小浏览器工作流、SQLite 持久化、素材选择、来源标签、必要追溯和手动重试。

### 2.2 真实 Provider 完成目标

- 工程保底通过后，至少真实接入一个文本模型和一个图像模型，且走相同 Provider 契约与业务流程。
- 真实图像若在 RTX 4060 8GB 上经许可后的实际安装、运行和资源测试最终无法完成，必须保留模型版本、配置、日志、峰值资源、耗时或 OOM 等证据，保留 ImageProvider 接口，并用 Mock 或自制合法素材完成替代演示。
- 上述硬件例外是“有证据的未达成说明”，不是从项目开始就把全部真实模型视为可选。

## 3. 工程保底必须完成的功能（P0）

### 3.1 项目与结构化创作

- 新建项目并输入中文短故事、标题和目标时长。
- 文本 Mock 输出版本化结构化剧本，含角色、场景和 3—5 个镜头。
- 校验镜头数量、总时长、字段、序号和引用关系。
- 用户可审核并编辑角色、场景、镜头时长、画面、运镜、旁白、台词和字幕。
- 上游编辑递增 revision，并使相关下游素材 `STALE`。

### 3.2 关键帧与镜头

- 图像 Mock 为每镜头产生至少一个有效、可预览的关键帧文件；重新生成保留历史候选。
- 用户为每镜头选择唯一关键帧。
- `FfmpegMotionVideoProvider` 根据关键帧和运镜模板生成片段，至少支持静止、缓慢推近、缓慢拉远、横向平移四类安全模板。
- 生成式视频 Provider 可以没有真实实现，但接口、Mock 和来源标记必须存在。

### 3.3 音频、字幕与导出

- TTS Mock 生成合法 WAV 占位音频，长度与镜头匹配并显示 `MOCK`，不宣称是中文语音。
- 每个镜头在进入导出前明确选择一个有效 clip 和一个有效 audio；Export 不隐式触发 Speech Job。
- 导出前根据已审核旁白/台词预览字幕时间轴；正式 UTF-8 SRT/ASS、SUBTITLE Asset 和烧录文件由 Export Job 确定性生成。
- 所有镜头先统一为目标分辨率、帧率、像素格式、采样率和声道，再进行拼接。
- FFmpeg 生成含视频流、音频流和烧录中文字幕的 MP4，同时保留字幕边车和 manifest。
- ffprobe 验证成片；不允许仅检查“文件存在”。

### 3.4 Job 与追溯

- SQLite Job 表、独立 Worker、默认并发 1。
- 第一版只显示 `QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`；FAILED 可由用户显式创建新的手动重试 Job。
- 第一版记录每个 Job 的 Provider/执行器、模型、提示词、参数、请求 seed、耗时、错误摘要和输出；单次 Job 的必要快照要可追溯。
- `CANCELLED`、`RETRY_WAIT`、自动重试、租约、心跳、崩溃恢复、客户端幂等键、复杂 CAS、Provider 多次调用历史和两阶段素材归档均为稳定后增强，不阻塞第一段成片或工程保底。
- `MOCK`、`DETERMINISTIC_FALLBACK`、`LOCAL_MODEL`、`REMOTE_API`、`USER_UPLOAD`、`DEMO_FIXTURE`、`SYSTEM_DERIVED` 七类来源在界面与导出清单中明确区分。

## 4. 真实 Provider 目标与加分项（按优先级）

### 4.1 真实 Provider 目标

1. 接入一个真实文本 Provider，候选优先为官方 Qwen GGUF + llama.cpp 服务；输出走与 Mock 相同的 Schema 校验。
2. 接入一个真实图像 Provider，优先验证 Animagine XL 4.0 Opt；若目标机实测失败，按第 2.2 节保留证据与替代演示。

### 4.2 质量与展示加分项

1. 专门的 Provider 健康与能力页面，以及更完整的 manifest 可视化/下载。
2. 用户上传自制或获许可的旁白，或真实 TTS。
3. 每镜头 2—3 个关键帧候选、SSE 进度、角色参考图与统一描述词注入。
4. 自动重试、取消、租约/心跳、崩溃恢复、客户端幂等、两阶段归档恢复和完整 Export 失效竞争语义。

加分项必须可关闭，关闭后工程保底不受影响。真实文本与真实图像仍需独立安装/下载许可与许可证复核，但二者属于真实 Provider 目标，不与纯展示加分项混写。

## 5. 明确不在当前范围内完成

- 不把任何本地生成式视频大模型作为项目成功条件。
- 不做长视频、1080p/4K、超过 5 镜头或多集项目。
- 不做角色 LoRA、模型训练、微调、数据集管理或权重下载管理。
- 不做骨骼动画、动作捕捉、口型同步、面部驱动或复杂特效。
- 不做 Premiere / After Effects 式多轨时间线和逐帧编辑。
- 不做多人实时协作、账号、权限、评论、云存储或公开分享。
- 不做多 GPU、多 Worker 调度、Redis、Celery、Kubernetes 或微服务。
- 不同时接入大量模型，不做自动模型排行榜或付费路由。
- 不做模型输出版权自动判定、内容安全分类器或生产级审核平台；仅通过原创故事、负面提示和人工审核降低风险。
- 不把网页聊天能力包装成平台运行时 Provider。

## 6. 固定演示故事建议

### 6.1 故事：《纸鹤的夜航》

原创角色“阿澄”是一名年轻的绘图学徒。雨夜停电时，他在工作台边折出一只纸鹤；纸鹤被窗外的微光点亮，飞过屋顶和安静街道，最后在天亮前带回一片发光的银杏叶。故事旁白主导，无复杂对话、群像、打斗或口型要求。

### 6.2 固定四镜头编排

| 镜头 | 时长 | 场景与动作 | 建议运镜 | 字幕/旁白意图 |
|---|---:|---|---|---|
| 1 | 7 秒 | 雨夜工作室，阿澄在烛光中折纸鹤 | 缓慢推近 | “停电的雨夜，阿澄折下最后一道纸痕。” |
| 2 | 7 秒 | 纸鹤发光，从掌心飞向打开的窗 | 缓慢拉远 | “一束微光，让纸做的翅膀醒了过来。” |
| 3 | 7 秒 | 纸鹤掠过屋顶与湿润街道 | 缓慢横向平移 | “它越过沉睡的屋顶，寻找夜色尽头的礼物。” |
| 4 | 7 秒 | 黎明工作室，纸鹤带回发光银杏叶 | 缓慢推近后淡出 | “天亮以前，一片银杏把远方带回了窗边。” |

计划总时长为 28 秒。产品允许 3—5 镜头和 20—40 秒，固定演示只是一组稳定 fixture，不能把“必须 28 秒”误写成产品通用限制。

固定 fixture 把 Scene 定义为可复用地点背景，共两个：工作室、屋顶与街道外景；雨夜/黎明等镜头级光照变化写入 Shot 的画面描述。若未来把 Scene 改成严格的“地点 + 时间场次”，必须相应增加场次，不能同时声称仍只有两个。

### 6.3 为什么适合作为演示

- 单主角和固定服装描述降低身份漂移。
- 纸鹤和银杏叶形成明显的跨镜头连续性证据。
- 两个主要场景可复用背景描述。
- 旁白主导，避开口型和多人对话。
- 低强度运镜适合静帧兜底，Mock 素材也能讲清故事。
- 全部为原创设定，避免使用知名动漫人物作为提示词或演示素材。

## 7. “20—40 秒成片”的具体定义

只有同时满足以下条件才称为成片：

- `ffprobe` 实测容器时长满足 `20.0 <= duration <= 40.0`，不能只相加数据库计划值。
- manifest 中存在 3—5 个有序镜头，每个镜头有已选择关键帧和实际使用的视频片段。
- 成片由平台根据数据库和素材自动导出，不允许依赖平台外人工剪辑。
- 目标输出为 1280×720、24 fps、方形像素、`yuv420p`；目标编码为 H.264 视频和 AAC 音频。编码器能否使用必须由下一阶段 FFmpeg 预检确认。
- 至少包含一个视频流和一个音频流；无真实语音时必须补齐合法音轨并明确标注 Mock。
- 中文字幕在画面内可见，并保留 UTF-8 SRT 或 ASS 文件。
- 音视频不能出现明显截断，字幕区间不得越过总时长；允许简单淡入淡出，不要求复杂转场。
- Edge、Chrome 或 Windows 常用播放器至少一个能够完整播放。
- 导出记录包含镜头、资产 SHA-256、来源、参数、FFmpeg/ffprobe 版本和验证结果。

## 8. 避免成为“模型按钮集合”的设计规则

1. 导航按制作阶段而不是按模型名称组织。
2. 每个 Job 必须引用已审核的业务 revision 和已选择的上游 Asset。
3. Provider 只决定“如何执行”，不决定业务实体和工作流。
4. 生成候选、人工选择、下游消费形成明确闭环。
5. 修改剧本、角色或镜头后，旧素材自动过期且导出被门禁拦截。
6. 导出前检查每个镜头的有效关键帧选择、片段选择、音频选择和字幕文本，错误信息列出具体缺项；字幕边车由这些已审核数据确定性生成。
7. 自动或手动 fallback 都记录完整尝试链；不得用 Mock 冒充模型能力。
8. 演示时展示一次“失败—重试或降级—继续导出”，把工程韧性作为核心能力。

## 9. 完成定义

### 9.1 工程保底完成

- 从空数据库、断网和无 API Key 环境开始，可以用固定故事走完全流程。
- 用户可在浏览器完成审核、编辑、生成、选择和导出，无需手改数据库或媒体文件。
- 生成 4 镜头、约 28 秒的合规 MP4，且 ffprobe 验证通过。
- FAILED 有清楚错误，手动重试会创建新 Job；不要求自动重试、取消或 Worker 租约恢复。
- 所有素材与导出可追溯，Mock 和兜底标签清楚。
- 重新启动 API 与 Worker 后数据不丢失，重新生成不覆盖旧资产。
- 文档中的范围、枚举、目录、验收与实际实现一致。

### 9.2 真实 Provider 完成

- 工程保底全部通过。
- 一个真实文本 Provider 通过固定故事的结构化输出验收。
- 一个真实图像 Provider 通过关键帧生成和来源追溯验收；若最终被硬件实测阻断，则提交完整证据、保留 Provider 接口与替代演示，并明确说明该目标未完全达成。

## 10. 范围变更规则

- M0 后冻结支持首段 MP4 的最小 Schema、Provider DTO 与文件规格；其余契约按里程碑逐步冻结。
- 新功能必须采用“一进一出”：新增一项时删除或延期同等工作量的非 P0 项。
- M1 首段 MP4 前不实现完整页面或高级 Job 机制。
- 工程保底稳定后按“真实文本 → 真实图像”推进真实 Provider 目标；每类只接一个首选 Provider。
- 进入演示冻结里程碑后只修复阻断缺陷，不再扩展范围。
- 任何需要新增基础设施、下载大型视频权重或训练模型的提议自动移出 MVP。
